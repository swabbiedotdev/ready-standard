# Working in ready-standard

This repository documents the `.ready` standard (Ready standard 8) as Ready
Room implements it and ships the `ready-standard` agent skill (the ready skill)
for writing a Ready Intent Package (RIP): the bundle of `.ready` files that
describes a product. Ready Room's code is the source of truth; this repository
follows it.

## Sources of truth, in order

1. Ready Room `app/src/shared/intent/types.ts`: the zod schema. Every field,
   enum, and required/optional choice.
2. Ready Room `app/src/shared/intent/model.ts`: the loader. Reference kinds,
   structural checks, validator codes and severities, size limits, and
   reachability.
3. Ready Room `app/scripts/ready.ts`: the CLI, run as `npm run ready --
   validate|export|schema`, and published as `@readyroom/ready`.
4. Ready Room `research/intent-model/ready-standard.md`: the approved Ready
   standard 8 specification, with its worked example and recorded decisions.
5. Ready Room `AGENTS.md` and `product/`: how the standard is used in practice.

The repository owner directs product-intent principles (`principles.md`); code
does not change them.

## Where things live

- `skills/ready-standard/references/format.md` is the one specification. Other
  files link to it rather than restating fields. `authoring.md` keeps a
  per-kind checklist and the templates keep per-kind field comments; both name
  fields only to guide work and must agree with `format.md`.
- `skills/ready-standard/assets/template-package/` is a valid package with a
  record of every kind. It must validate with 0 errors and 0 warnings.
- `skills/ready-standard/assets/ready.schema.json` is generated by Ready Room;
  never edit it by hand.

## Keeping in sync with Ready Room

Do this whenever `types.ts`, `model.ts`, the CLI script, or `ready-standard.md`
changes in Ready Room:

1. In the Ready Room checkout, `git log -p <last synced commit>.. -- app/src/shared/intent/types.ts app/src/shared/intent/model.ts app/scripts/ready.ts research/intent-model/ready-standard.md`.
2. Regenerate the schema:
   `npm --prefix <ready-room> run ready -- schema "$PWD/skills/ready-standard/assets/ready.schema.json"`.
3. Update `references/format.md` for each added, removed, or changed field,
   enum value, reference kind, validator code, severity, or size limit. Then
   update the affected per-kind checklist entries in `authoring.md`, the field
   comments in the templates, and `validation.md` or `mistakes.md` if a check
   changed.
4. If `READY_SCHEMA` changes (a new `ready:` version), update every template
   and the version in `format.md`'s title, and rewrite every reference for the
   new standard. The skill teaches only the current standard.
5. If CLI commands or flags change, update `reading.md`, `validation.md`,
   `SKILL.md`, and `README.md`.
6. Run `scripts/check.sh <ready-room-checkout>`; it must pass.
7. Update **Current sync** above with the release and commit.

Never document a field Ready Room does not accept, and never describe a check
the loader does not run. If the standard needs something new, it is added to
Ready Room's schema first.

## Writing in this repository

- Call the bundle of `.ready` files a Ready Intent Package (spelled out with
  "(RIP)" on first use in each document), then RIP, ready package, or `.ready`
  package.
- Ready Room's copy of a product's RIP is the "Ready Room RIP" (or "working
  RIP", "RIP in Ready Room"); the copy in the product's repository is the
  "repository RIP". Never "cloud RIP".
- Ready Room contract names, cited only where needed and exactly as named: the
  HTTP and MCP tool `read_rip`, message kind `rip_change`, MCP prompt
  `rip_authoring_guidance`, resource `ready-room://guidance/rip-format`, CLI
  `rr rip`, plugin skill `rip-authoring`, D1 table `cloud_rip`, and the R2
  prefix `pip/` (unchanged).

- Every YAML example that is a whole record (`ready: 2` …) must validate: put new
  ones in the template package or check them in a scratch package with the
  validator.
- Write principles and guidance in the present tense, as current rules. No
  changelog or history in the docs; Git holds it.
- Keep `SKILL.md` short; detail goes in `references/`, loaded on demand.
- State principles in `.ready` terms (capabilities, records, fields, ids,
  edges, parts, supplementary files). Teach only the current standard: no
  earlier formats, mappings from them, or compatibility notes.
